## 5. 사람과 협업한다는 목적에서 본 진단

### 결정 지점이 실제 작업 방식과 다른 곳
- PR이 사람 검토 지점이라는 설계(0012: "판단은 PR에서")와 실제가 다르다. 16개 PR에 사람 코멘트 0건, '판단할 곳' 16개 모두 "없음". 사용자의 판단은 전부 대화에서 나왔고 PR은 병합 버튼으로만 쓰였다. 그래서 `pre-pr-review`의 판단할 곳 정리, 0053의 "PR 판단할 곳에서 확인"처럼 PR에 판단을 미루는 장치는 실제로는 판단을 받지 못한다. 사용자의 실제 검토 지점은 대화의 승인 A·B·배포 승인과 하네스 회고 대화다. PR 검토는 규칙·테스트 확인 게이트로 보고, 사용자 판단은 대화에서 받도록 맞추는 편이 실제와 같다(내 추론).
- 피드백은 대화 → 메인이 그날 결정 파일 + 하네스 PR로 돌아왔다. 관찰 단계가 없어 사례 하나가 규칙 하나가 됐다(evolve 원칙 "일반화 없는 반영 금지"). PR 코멘트 경로(evolve 로컬 5)는 이 저장소에서 비어 있다.

### 결정을 너무 많이 받는 곳
- 하네스 절차의 세부(0053 결정 형식, 0052 측정 방식, 0032 4항 경로 같은 연결 누락 수정)까지 결정 파일과 사용자 합의를 거쳤다. governance 2절은 "앞 결정의 의도가 덮는 새 사례", "사소한 경로"를 메인이 정하고 기록하라고 한다. 하네스 결정 17건 가운데 0032 4항, 0052, 0053은 메인 기본값으로 둘 수 있었다(내 판단).

### 결정을 너무 늦게 받은 곳
- 구축 때 운영 틀(공개 저장소, PR·리뷰 방식, 판정 방법, 화면 확인 방식)을 묻지 않아 첫날 5시간 동안 사용자가 하네스 결정을 연달아 내렸다(2.6).

### 화면을 보기 전에 결정을 요구한 곳
- 승인 B의 이력 축: 글과 ASCII로 승인 → 구현 뒤 점이 된 막대 → 0042에서 축 제거 → 0050. 0050이 고친 것은 맞다.
- 0036 2항의 수용 범위 숫자도 기획안 글로 승인 B에서 함께 승인받게 돼 있다. 수용 범위는 실제 분포가 화면에서 어떻게 보이는지에 달려 있어 같은 위험이 있다. 0050의 그림 요소 목록처럼 "렌더로 확인한 범위인가"를 표시하는 대상에 넣을지 볼 만하다.
- 데모 배포 승인은 전후 스크린샷을 함께 보이게 설계돼 있어 이 문제가 없다.

## 6. 불확실한 점

- 분류가 갈리는 것: 12번(`astro check`)은 사실 확인 실패로 보면 A, 확인 없이 쓴 문서 전제로 보면 B. 30번(미리보기 서버)은 Windows 프로세스 동작이라 A로 뒀지만 백그라운드 서버 수명 관리를 구축 때 정할 수 있었다고 보면 B. 36번(0048)은 사용자 선호(미루는 쪽)가 새로 드러난 것으로 보면 A. 42번(데모 트랙)은 0021 시점에 예고된 일이라 B로 볼 수도 있다.
