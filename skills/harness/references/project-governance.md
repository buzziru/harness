# 프로젝트 운영 틀 설계 (로컬 추가)

> 로컬 포크에서 더한 문서다. 근거는 meet-rag(2026-09\~11, 하네스 ADR 107건)와 portfolio(2026-11, 하네스 감사 2026-11-10)이고, 한 프로젝트에서만 나온 항목은 가설이다. 출처와 검증 상태는 저장소 루트 `LOCAL_CHANGES.md`에 있다.

에이전트 팀 구조만 정하면 하네스가 어떤 판단을 사용자에게 넘길지, 무엇을 막을지, 결정을 어디에 남길지가 비어 있다. 이 빈칸은 하네스를 고칠 때마다 다시 문제가 되므로, 하네스를 처음 만들 때(1·2단계)와 고칠 때(7단계, `harness:evolve`) 모두 이 문서를 읽는다.

## 목차

1. 판정 방법
2. 승인 지점과 자율 범위
3. 보호 장치
4. 결정 기록
5. 사람 검토 지점
6. `_workspace/` 수명 주기
7. 종료
8. 규칙과 강제 장치

## 1. 판정 방법

1단계에서 "최종 산출물을 무엇으로 판정하는가"를 묻는다.

- 판정이 주어진 프로젝트(테스트 통과, 대회 지표, 사용자 확인)는 그 판정을 하네스의 검증 단계에 그대로 연결한다
- 판정이 주어지지 않은 프로젝트(생성 품질, 연구 결과)는 첫 하네스에 최종 산출물을 채점하는 최소 경로를 넣는다. 설계가 덜 됐으면 기성 도구를 붙여 점수만 나오게 두고 나중에 고친다
- 평가기를 직접 만들면 고치기를 멈출 기준을 먼저 정한다: 같은 입력의 반복 흔들림 안의 차이는 노이즈로 보고, 판정을 뒤집는 오류만 고치고, 답을 일부러 망가뜨려 평가기가 잡는지 시험한다

이유: 앞 단계만 평가하고 최종 산출물의 평가를 미루면, 평가기를 만드는 동안 앞 단계 결과를 다시 봐야 하고 평가기 수정이 끝없이 이어진다(meet-rag: 생성 평가 모듈 6.5작업일, judge 지시 j_v2\~j_v13).

## 2. 승인 지점과 자율 범위

2단계에서 사용자에게 묻는 일과 메인이 정하는 일을 나눠 오케스트레이터에 적는다.

| 사용자에게 묻는다 | 메인이 정하고 기록한다 |
| --- | --- |
| 되돌리기 어려운 일(평가 기준, 외부 공개, 데이터 삭제) | 앞 결정의 의도가 덮는 새 사례 |
| 비용·위험을 새로 감수하는 일(유료 호출, 외부 GPU) | 값·문구 대조처럼 저장소를 읽으면 닫히는 질문 |
| 해석이 둘 이상이고 동작이 갈리는 지시 | 사소한 표현·경로 이름, 하네스 절차 세부(측정 방식, 이력·결정 기록 형식, 연결 누락 수정) |

- 자율 범위는 첫날부터 넓게 두고, 사고가 나면 좁힌다. 메인이 하위 에이전트를 거치지 않고 직접 고쳐도 되는 경계는 크기(몇 줄)가 아니라 종류(검증 단계를 거쳐야 하는 산출물인가)로 정한다
- 메인이 정한 것은 묻지 않고 결정 번호와 입력→동작 사례로 남겨 보고에 적는다. 사용자는 보고에서 어긋남을 본다
- 사용자는 앞 결정과 원자료를 기억에 기대 답한다. 그래서 질문마다 (가) 무엇에 대한 판단이고 어디에 쓰이는지 (나) 왜 생겼는지(결정·규칙은 번호만 대지 않고 내용을 한두 문장으로, 그 결정이 무엇을 덮지 못하는지) (다) 선택지마다 실제로 달라지는 것(구체 예, 수치) (라) 추천과 이유를 담고, 질문 대화상자만 보여도 판단할 수 있게 질문 문장에도 가·나의 핵심을 넣는다. 사용자 답이 기록과 다르면 기록의 경로와 해당 문장을 보이고 다시 확인한다. 질문을 반환하는 에이전트, 하위 세션, `harness:evolve` 반영 전 관문의 질문도 같은 형식이고, 프로젝트에서는 이 형식을 정본 한 곳에 두고 질문을 만드는 자리는 경로만 가리킨다

이유: 좁게 시작하면 작은 판단까지 사용자에게 넘어가 리뷰가 병목이 된다. 병목은 작업 수가 아니라 작업마다 넘어간 판단의 개수였다(meet-rag ADR-0041, 0077: PR 결정 항목 54개 중 23개가 원안대로 닫힘).

## 3. 보호 장치

1단계에서 이 프로젝트의 되돌리기 어려운 일을 목록으로 뽑고, 2단계에서 장치마다 막을 곳을 정한다.

- 대상 예: 공유 데이터 삭제, 평가 데이터 오염(test 읽기, 보호 경로 수정), 비밀 값 출력, 외부 전송, 공개 저장소 커밋, 저장소 밖 파일·서비스 수정(다른 저장소, 배포된 데모)
- 장치: 사전 훅(명령을 막거나 확인을 띄움), 권한 거부 규칙, 커밋 전·PR 전 감사 에이전트
- 프로젝트 `CLAUDE.md`에 처음부터 둔다: "지우기, 보호 해제, 권한 완화 요청, 외부 전송 전에는 대상과 그것을 지키는 장치를 먼저 확인한다. 막혔으면 원인을 확인하기 전에 우회를 제안하지 않는다"
- 장치는 사용자가 말한 위험만 막는다. 정당한 작업에 확인 창이 늘면 걷어낸다

이유: 사고는 대상과 보호 장치를 확인하지 않고 움직인 데서 났고, 사고마다 규칙을 하나씩 더하면 다른 장치 앞에서 같은 습관이 다시 나왔다(meet-rag ADR-0058: junction을 따라간 삭제, 거부 규칙을 확인하지 않은 권한 완화 요청).

## 4. 결정 기록

- 프로젝트 결정(데이터·모델·평가)과 하네스 결정(스킬·에이전트·규약)을 나눈다
- 하네스 변경 이력이 열 건을 넘으면 `CLAUDE.md` 표 대신 결정 하나에 파일 하나(`docs/harness/adr/NNNN.md`)로 두고, `CLAUDE.md`에는 위치만 적는다. `CLAUDE.md`는 매 세션 읽혀 표가 길어지면 다른 지시가 묻힌다
- 사용자 답을 받은 자리에서 다음 단계로 넘어가기 전에 결정 파일 초안을 쓴다. 승인 지점의 답뿐 아니라 메인 제안에 대한 동의·거절, 범위를 넣고 빼는 답도 같다. 산출물(PR 등)을 낼 때는 대화를 훑어 빠진 파일이 없는지만 확인한다. 몰아 쓰면 빠진 답이 산출물 검토에서야 드러난다
- 결정 파일에는 상태, 맥락, 결정, 결과, 삭제 조건을 둔다. 삭제 조건은 규칙을 걷어낼 근거가 된다(예: 일회성 데이터 생성용 작업자는 세트를 동결하면 지운다)
- 앞 결정을 바꾸면 앞 기록의 원문은 두고 줄 끝에 무엇이, 왜(어떤 조건이 변해서) 바뀌었는지 표시한다
- 규칙 본문에는 절차와 이유만 두고 사고 사례는 결정 기록에 둔다. 사례가 규칙 안에 쌓이면 규칙을 다른 프로젝트로 옮기기 어렵다

## 5. 사람 검토 지점

에이전트끼리의 검증과 별도로, 사람이 결과를 받는 지점과 그때 보는 것을 정한다. 화면·실행 결과로 판단할 산출물(렌더된 화면, 그림, 데모)은 글 설명이 아니라 그 결과를 보여 주고 승인받는다. 승인 자료에는 새로 생기거나 바뀌는 그림 요소 목록을 두고 요소마다 실제 데이터로 렌더했는지 표시한다. 렌더하지 못한 요소는 승인이 덮지 않고, 구현 뒤 렌더로 다시 확인받는다.

- 사용자 판단은 작업 중 대화에서 받아 바로 결정 기록으로 남긴다. 산출물(PR 등)에 붙이는 검토 안내에는 이미 정한 것의 요약, 되돌리기 어려운 변경, 사람이 볼 곳, 읽지 않아도 되는 부분을 적는다. 아직 정하지 않은 판단이 남았으면 산출물을 내기 전에 대화에서 묻는다
- 검토 안내는 작성 맥락과 분리한 에이전트가 쓴다. 안내를 쓴 뒤 산출물을 고쳤으면 고친 산출물로 다시 받는다
- PR 하나의 범위와 작업 중 새로 나온 일의 기본값(같은 PR에 넣는다, 대기 목록으로 미룬다)을 정한다. 원래 산출물이 그 자체로 맞으면 새 과제는 나눠서 다룬다

이유: 판단할 곳이 추려지지 않으면 사용자가 전체를 읽어야 하고, 답이 필요 없는 질문 사이에 판단할 질문이 묻힌다(meet-rag `pr-briefer`, ADR-0041). 판단을 PR로 미루면 사용자는 이미 대화에서 답한 뒤라 PR에서는 판단이 나오지 않는다(portfolio: PR 16개의 판단할 곳이 모두 "없음").

## 6. `_workspace/` 수명 주기

`SKILL.md` 5-1의 `_workspace/` 규칙에 더한다.

- `_workspace/`는 단계 사이 전달과 진행 기록용이다. 최종 결과와 결정은 추적되는 문서로 옮기고 `_workspace/`만 기록처로 쓰지 않는다
- 원본 데이터에서 나온 내용(질의, 원문, 실행 로그)이 섞이면 공개 저장소에 올리지 않는다. 그런 파일은 이름이나 하위 폴더로 구분한다
- worktree를 쓰면 `_workspace/`는 메인 체크아웃에 두고 worktree 세션은 메인 경로를 읽는다. `.gitignore` 대상이라 worktree를 지울 때 경고 없이 함께 지워진다
- 하네스 개선 거리는 `_workspace/` 안의 대기 목록 한 파일에 상태(대기, 관찰, 반영, 닫음)와 함께 적는다(`harness:evolve` 참고)

## 7. 종료

프로젝트를 마칠 때 한다.

1. 회고: 프로젝트 내용과 하네스 운영을 나눠 쓴다. 하네스 회고는 다음 `/harness`의 입력이다
2. 가져갈 것과 두고 갈 것을 나눈다. 프로젝트 고유 절차, 도메인 규칙, 사고 사례는 두고 간다. 역할, 틀, 훅은 테스트와 함께 가져간다
3. 다시 만들 수 없는 산출물(사람 검수 결과, LLM으로 만든 평가 세트, 유료 호출 기록)을 목록으로 뽑아 보관한다. 다시 만들 수 있는 것은 지문(SHA-256)만 문서에 남긴다
4. `_workspace/`는 보관하거나 지운다. 결론은 이미 추적 문서에 있어야 한다
5. 병행 세션과 worktree를 정리한다

## 8. 규칙과 강제 장치

되풀이된 실패를 고칠 때 규칙 문장을 고칠지, hook·테스트·CI 같은 장치를 더할지 정하는 기준이다. `harness:evolve` 반영 전 관문(가·나)을 거친 항목에 적용한다. 1절 판정 방법, 3절 보호 장치, `SKILL.md` 6-7 화면 판정 장치처럼 구축 때 두는 장치는 되풀이를 기다리지 않으므로 이 기준에 해당하지 않는다.

- 장치는 두 조건을 모두 갖춘 실패에만 더한다. (1) 규칙 문장이나 그 문장이 불리는 위치를 고친 뒤에도 같은 실패가 되풀이됐다 (2) 실패를 기계로 판정할 수 있다(명령, 파일 내용, 검사 결과로 참·거짓이 갈린다)
- 자연어 판단이 필요한 실패(질문 형식, 정본과의 대조, 범위 판단)는 규칙과 작성 맥락이 없는 분리 검토로 둔다. 장치로 만들면 잘못 잡거나 놓친 경우를 사람이 다시 판정해야 해서 확인 창만 는다
- 장치를 더할 때는 3절처럼 막을 대상과 삭제 조건을 결정 기록에 적는다

| 실패 종류 | 판단 | 이유 |
| --- | --- | --- |
| 사용자 질문에 맥락이 빠짐(2절) | 규칙, 질문을 반환하는 자리의 분리 검토 | 맥락이 충분한지는 자연어 판단이다 |
| 결정 파일 누락(4절) | 쓰는 위치를 답 직후로 옮긴 뒤 다시 나기 전까지 관찰. 다시 나면 사용자 답 직후 알림 hook을 후보로 둔다 | 쓰는 위치를 고친 뒤 재발했는지가 (1) 조건이다 |
| 재검증 범위가 매 라운드 전체(`team-patterns.md` 1-4) | 규칙 | 변경분이 어디까지인지는 검토자가 판단한다 |
| 렌더하지 않은 요소의 승인(5절) | 규칙 | 승인 자료의 표시 여부는 사람이 본다 |
| 정본이 바뀐 뒤 하네스 파일에 옛 규칙이 남음(`SKILL.md` 4-5) | 규칙과 PR 전 검토 점검. 옛 이름·값을 grep으로 찾는 검사는 낱말이 정해진 경우에만 테스트로 | 무엇이 옛 규칙인지는 대개 의미 판단이다 |
| 화면 판정이 사람마다 다름 | 이 기준 밖. 구축 때 장치(측정 스크립트, `SKILL.md` 6-7) | 판정 방법의 일부라 되풀이를 기다리지 않는다 |
| main 직접 푸시, 필수 검사 없이 병합, 새 메시지 옵션 없는 amend, 화면 문자열의 금지 기호 | 장치(보호 규칙, CI 필수 검사, 사전 hook, 테스트) | 명령이나 문자열로 판정된다 |
| 외부 worker 권한, 하위 세션 운용(`parallel-sessions.md`) | 규칙 | 환경마다 다르고 사례가 적다 |
