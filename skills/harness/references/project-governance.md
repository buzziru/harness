# 프로젝트 운영 틀 설계 (로컬 추가)

> 로컬 포크에서 더한 문서다. 근거는 meet-rag(2026-09\~11, 하네스 ADR 107건)와 portfolio(2026-11, 하네스 감사 2026-11-10)이고, 한 프로젝트에서만 나온 항목은 가설이다. 출처와 검증 상태는 저장소 루트 `LOCAL_CHANGES.md`에 있다.

에이전트 팀 구조만 정하면 하네스가 어떤 판단을 사용자에게 넘길지, 무엇을 막을지, 결정을 어디에 남길지가 비어 있다. 이 빈칸은 하네스를 고칠 때마다 다시 문제가 되므로, 하네스를 처음 만들 때(1·2단계)와 고칠 때(7단계, `harness:evolve`) 모두 이 문서를 읽는다.

## 목차

1. 판정 방법
2. 승인 지점과 자율 범위
3. 보호 장치
4. 결정 기록
5. 사람 검토 지점
6. `_workspace/` 수명 주기
7. 종료
8. 산출물 검증과 행동 강제 장치

## 1. 판정 방법

1단계에서 "최종 산출물을 무엇으로 판정하는가"를 묻는다.

- 판정이 주어진 프로젝트(테스트 통과, 대회 지표, 사용자 확인)는 그 판정을 하네스의 검증 단계에 그대로 연결한다
- 판정이 주어지지 않은 프로젝트(생성 품질, 연구 결과)는 첫 하네스에 최종 산출물을 채점하는 최소 경로를 넣는다. 설계가 덜 됐으면 기성 도구를 붙여 점수만 나오게 두고 나중에 고친다
- 평가기를 직접 만들면 고치기를 멈출 기준을 먼저 정한다: 같은 입력의 반복 흔들림 안의 차이는 노이즈로 보고, 판정을 뒤집는 오류만 고치고, 답을 일부러 망가뜨려 평가기가 잡는지 시험한다

이유: 앞 단계만 평가하고 최종 산출물의 평가를 미루면, 평가기를 만드는 동안 앞 단계 결과를 다시 봐야 하고 평가기 수정이 끝없이 이어진다(meet-rag: 생성 평가 모듈 6.5작업일, judge 지시 j_v2\~j_v13).

## 2. 승인 지점과 자율 범위

2단계에서 사용자에게 묻는 일과 메인이 정하는 일을 나눠 오케스트레이터에 적는다.

| 사용자에게 묻는다 | 메인이 정하고 기록한다 |
| --- | --- |
| 되돌리기 어려운 일(평가 기준, 외부 공개, 데이터 삭제) | 앞 결정의 의도가 덮는 새 사례 |
| 비용·위험을 새로 감수하는 일(유료 호출, 외부 GPU) | 값·문구 대조처럼 저장소를 읽으면 닫히는 질문 |
| 해석이 둘 이상이고 동작이 갈리는 지시 | 사소한 표현·경로 이름, 하네스 절차 세부(측정 방식, 이력·결정 기록 형식, 연결 누락 수정) |

- 자율 범위는 첫날부터 넓게 두고, 사고가 나면 좁힌다. 메인이 하위 에이전트를 거치지 않고 직접 고쳐도 되는 경계는 크기(몇 줄)가 아니라 종류(검증 단계를 거쳐야 하는 산출물인가)로 정한다
- 메인이 정한 것은 묻지 않고 변경 이력 한 줄(입력→동작)로 남겨 보고에 적는다. 사용자는 보고에서 어긋남을 본다
- 사용자는 앞 결정과 원자료를 기억에 기대 답한다. 그래서 질문마다 (가) 무엇에 대한 판단이고 어디에 쓰이는지 (나) 왜 생겼는지(결정·규칙은 번호만 대지 않고 내용을 한두 문장으로, 그 결정이 무엇을 덮지 못하는지) (다) 선택지마다 실제로 달라지는 것(구체 예, 수치) (라) 추천과 이유를 담고, 질문 대화상자만 보여도 판단할 수 있게 질문 문장에도 가·나의 핵심을 넣는다. 사용자 답이 기록과 다르면 기록의 경로와 해당 문장을 보이고 다시 확인한다. 질문을 반환하는 에이전트, 하위 세션, `harness:evolve` 반영 전 관문의 질문도 같은 형식이고, 프로젝트에서는 이 형식을 정본 한 곳에 두고 질문을 만드는 자리는 경로만 가리킨다
- 근거(사실·경위)를 묻는 질문은 문장마다 묻지 않고 주제 하나에 질문 하나로 묻는다. 검증·리뷰가 낸 처방 가운데 같은 주제에 걸린 것을 모아 그 주제의 흐름 전체를 묻는다. 묻기 전에 같은 주제의 기존 사용자 설명(4절의 사실 기록)을 찾고, 있으면 질문에 인용하고 무엇이 빠졌는지 밝혀 새 측면만 묻는다. 다시 묻는 것을 막지는 않는다. 다시 물으며 지시가 정확해지는 일도 있다

이유: 좁게 시작하면 작은 판단까지 사용자에게 넘어가 리뷰가 병목이 된다. 근거 질문을 문장의 읽힘마다 하면 답으로 고친 문장이 다시 새로 읽혀 같은 주제를 거듭 묻게 되고, 답이 문장마다 조각나 쌓이지 않는다. 병목은 작업 수가 아니라 작업마다 넘어간 판단의 개수였다(meet-rag ADR-0041, 0077: PR 결정 항목 54개 중 23개가 원안대로 닫힘).

## 3. 보호 장치

1단계에서 이 프로젝트의 되돌리기 어려운 일을 목록으로 뽑고, 2단계에서 장치마다 막을 곳을 정한다.

- 대상 예: 공유 데이터 삭제, 평가 데이터 오염(test 읽기, 보호 경로 수정), 비밀 값 출력, 외부 전송, 공개 저장소 커밋, 저장소 밖 파일·서비스 수정(다른 저장소, 배포된 데모)
- 장치: 사전 훅(명령을 막거나 확인을 띄움), 권한 거부 규칙, 커밋 전·PR 전 감사 에이전트
- 프로젝트 `CLAUDE.md`에 처음부터 둔다: "지우기, 보호 해제, 권한 완화 요청, 외부 전송 전에는 대상과 그것을 지키는 장치를 먼저 확인한다. 막혔으면 원인을 확인하기 전에 우회를 제안하지 않는다"
- 장치는 사용자가 말한 위험만 막는다. 정당한 작업에 확인 창이 늘면 걷어낸다

이유: 사고는 대상과 보호 장치를 확인하지 않고 움직인 데서 났고, 사고마다 규칙을 하나씩 더하면 다른 장치 앞에서 같은 습관이 다시 나왔다(meet-rag ADR-0058: junction을 따라간 삭제, 거부 규칙을 확인하지 않은 권한 완화 요청).

## 4. 결정 기록

- 프로젝트 결정(데이터·모델·평가)과 하네스 결정(스킬·에이전트·규약)을 나눈다
- 하네스 변경 이력은 처음부터 `CLAUDE.md` 밖의 이력 파일 하나(예: `docs/harness/CHANGELOG.md`)에 표로 두고, `CLAUDE.md`에는 위치만 적는다. `CLAUDE.md`는 매 세션 읽혀 표가 길어지면 다른 지시가 묻힌다. 이력을 결정 하나에 파일 하나로 나누지 않는다. 변경마다 파일을 두면 아래 결정 수명 규칙과 반대로 파일이 쌓인다
- 결정 파일은 산출물·검증(8-1)으로 옮길 수 없는 사용자 판단(승인 지점의 답, 방향을 정하는 답)에만 쓴다. 정본이나 검증을 바꾸는 것으로 끝나는 답은 그 커밋과 변경 이력 한 줄이면 된다. 결정 파일이 필요한 답은 받은 자리에서 다음 단계로 넘어가기 전에 초안을 쓴다. 산출물(PR 등)을 낼 때는 대화를 훑어 빠진 파일이 없는지만 확인한다. 몰아 쓰면 빠진 답이 산출물 검토에서야 드러난다
- 결정 파일에는 상태, 맥락, 결정, 결과, 삭제 조건을 둔다. 삭제 조건은 규칙을 걷어낼 근거가 된다(예: 일회성 데이터 생성용 작업자는 세트를 동결하면 지운다)
- 앞 결정을 바꾸면 앞 기록의 원문은 두고 줄 끝에 무엇이, 왜(어떤 조건이 변해서) 바뀌었는지 표시한다
- 결정은 정본이나 검증에 반영되면 닫는다. 그 뒤 작업 규칙의 출처는 정본과 검증이고, 결정 파일은 이유를 찾을 때만 읽는다
- 정본과 하네스 파일에 결정 번호를 적지 않는다. 결정 파일 쪽에서 바꾼 정본 위치를 적는다. 번호를 정본에 적으면 결정을 바꿀 때마다 그 번호가 적힌 파일을 모두 고쳐야 하고, 번호 정합을 검사하는 장치까지 생긴다
- 결정 파일이 쌓이면 유효한 사용자 판단만 요약 한 파일로 모으고 개별 파일은 보관 폴더로 옮긴다
- 사용자가 판단이 아니라 사실·경위를 설명한 답은 결정 파일이 아니라 사실 기록(사실표처럼 근거를 행으로 모으는 표)에 둔다. 주제 하나에 행 하나로 두고 결론 조각이 아니라 요지 전체(경위, 순서, 판단 기준)를 적는다. 같은 주제의 답이 다시 오면 새 행을 만들지 않고 그 행에 날짜를 붙여 덧붙인다. 결론 조각만 남기면 다음 리뷰가 같은 주제를 다른 문장으로 다시 열 때 이미 답한 것으로 알아보지 못한다
- 규칙 본문에는 절차와 이유만 두고 사고 사례는 결정 기록에 둔다. 사례가 규칙 안에 쌓이면 규칙을 다른 프로젝트로 옮기기 어렵다

### 4-1. 운영 틀 기록과 하네스 목록 파일 형식

1단계 7의 답(1\~5절과 git·PR 흐름)은 운영 틀 기록(frame) 한 파일에만 둔다. 오케스트레이터와 `CLAUDE.md` Git 절에는 그 답을 적용한 절차만 두고 답(값과 출처)이나 결정 번호를 다시 적지 않는다. 같은 답이 두 곳에 있으면 바꿀 때 한쪽이 남는다. 아래 형식은 `harness` 스킬의 `scripts/check-harness.mjs`가 검사한다. 검사는 형식만 보고 답의 질은 보지 않는다(8-1).

하네스 목록 파일 `.claude/harness.json`은 검사가 프로젝트마다 다른 경로를 찾는 곳이다. 1단계 7을 마칠 때 쓴다.

```json
{
  "frame": "docs/harness/frame.md",
  "orchestrator": ".claude/skills/<오케스트레이터>/SKILL.md",
  "changelog": "docs/harness/CHANGELOG.md",
  "gitFlow": "light"
}
```

- `frame`, `orchestrator`, `changelog`는 프로젝트 루트 기준 경로다. `changelog`는 이력 표가 있는 파일(`CLAUDE.md`도 된다)이거나 결정 하나에 파일 하나를 두는 폴더다
- `gitFlow`는 `none`(넣지 않음), `light`(가벼운 흐름), `full`(전체 흐름)이다(`git-pr-flow.md` 1절)

frame 파일에는 절 여섯을 이 제목 그대로 둔다: `## 판정 방법`, `## 승인 지점과 자율 범위`, `## 보호 장치`, `## 결정 기록`, `## 사람 검토 지점`, `## git·PR 흐름`. 절마다 두 줄을 둔다.

- `- 답: <답>`
- `- 출처: 사용자 YYYY-MM-DD "<사용자 답 인용>"` 또는 `- 출처: 메인`. 결정 기록을 뺀 다섯 절은 2절 표의 '사용자에게 묻는다'와 1단계 7에 따라 `사용자`여야 한다. 인용을 요구하는 것은 묻지 않고 넘어간 답이 형식 위반으로 드러나게 하려는 것이다

보호 장치 절에는 3절의 되돌리기 어려운 일을 하나 이상 `- 대상: <일>`로 두고, 그 아래 들여 쓴 줄로 막는 곳을 적는다.

- `  - 장치: <루트 기준 경로> [설명]`: hook, 검사 스크립트, 감사 에이전트, CI 설정 파일. 경로가 있는지 검사한다
- `  - 장치: deny <규칙>`: `.claude/settings.json`이나 `settings.local.json`의 `permissions.deny`에 있는 규칙을 글자 그대로
- `  - 장치 없음: <이유>`

git·PR 흐름 절은 `gitFlow`가 `none`이 아니면 `git-pr-flow.md` 2절 표에서 고른 수준의 항목(가벼운 흐름은 '가벼운' 항목, 전체 흐름은 둘 다)마다 `- <항목 이름>: <값>` 줄을 둔다. 기본 프리셋을 따르면 값을 `기본`으로 쓰고, 다른 값이면 값 뒤에 `이유: <이유>`를 붙인다.

하네스 변경 이력은 변경마다 그 변경의 이행을 보는 장치를 `장치: <검사·hook>` 또는 `장치 없음: <이유>`로 적는다. 이력이 표 하나면 표 앞 설명이나 표 머리에 이 칸을 밝히고, 폴더면 폴더의 `README.md`(파일 형식 설명)에 `장치:` 줄을 두고 파일마다 적는다. 장치를 먼저 따지게 해서 규칙 문장만 더하는 변경이 보이게 한다(8절).

## 5. 사람 검토 지점

에이전트끼리의 검증과 별도로, 사람이 결과를 받는 지점과 그때 보는 것을 정한다. 화면·실행 결과로 판단할 산출물(렌더된 화면, 그림, 데모)은 글 설명이 아니라 그 결과를 보여 주고 승인받는다. 화면은 미리보기 서버 주소를 주고 사용자가 직접 보게 한다. 스크린샷 묶음을 만들어 보이는 것보다 빠르고, 사용자가 폭과 상태를 바꿔 볼 수 있다. 승인 화면에는 시안 문구가 아니라 실제 콘텐츠를 넣는다. 시안 문구로 승인한 형식은 실제 문장이 들어간 뒤에야 문제가 드러난다. 승인 자료에는 새로 생기거나 바뀌는 그림 요소 목록을 두고 요소마다 실제 데이터로 렌더했는지 표시한다. 렌더하지 못한 요소는 승인이 덮지 않고, 구현 뒤 렌더로 다시 확인받는다.

- 사용자 판단은 작업 중 대화에서 받아 바로 결정 기록으로 남긴다. 산출물(PR 등)에 붙이는 검토 안내에는 이미 정한 것의 요약, 되돌리기 어려운 변경, 사람이 볼 곳, 읽지 않아도 되는 부분을 적는다. 아직 정하지 않은 판단이 남았으면 산출물을 내기 전에 대화에서 묻는다
- 검토 안내는 작성 맥락과 분리한 에이전트가 쓴다. 안내를 쓴 뒤 산출물을 고쳤으면 고친 산출물로 다시 받는다
- PR 하나의 범위와 작업 중 새로 나온 일의 기본값(같은 PR에 넣는다, 대기 목록으로 미룬다)을 정한다. 원래 산출물이 그 자체로 맞으면 새 과제는 나눠서 다룬다

이유: 판단할 곳이 추려지지 않으면 사용자가 전체를 읽어야 하고, 답이 필요 없는 질문 사이에 판단할 질문이 묻힌다(meet-rag `pr-briefer`, ADR-0041). 판단을 PR로 미루면 사용자는 이미 대화에서 답한 뒤라 PR에서는 판단이 나오지 않는다(portfolio: PR 16개의 판단할 곳이 모두 "없음").

## 6. `_workspace/` 수명 주기

`SKILL.md` 5-1의 `_workspace/` 규칙에 더한다.

- `_workspace/`는 단계 사이 전달과 진행 기록용이다. 최종 결과와 결정은 추적되는 문서로 옮기고 `_workspace/`만 기록처로 쓰지 않는다
- 원본 데이터에서 나온 내용(질의, 원문, 실행 로그)이 섞이면 공개 저장소에 올리지 않는다. 그런 파일은 이름이나 하위 폴더로 구분한다
- worktree를 쓰면 `_workspace/`는 메인 체크아웃에 두고 worktree 세션은 메인 경로를 읽는다. `.gitignore` 대상이라 worktree를 지울 때 경고 없이 함께 지워진다
- 하네스 개선 거리는 `_workspace/` 안의 대기 목록 한 파일에 상태(대기, 관찰, 반영, 닫음)와 함께 적는다(`harness:evolve` 참고)

## 7. 종료

프로젝트를 마칠 때 한다.

1. 회고: 프로젝트 내용과 하네스 운영을 나눠 쓴다. 하네스 회고는 다음 `/harness`의 입력이다
2. 가져갈 것과 두고 갈 것을 나눈다. 프로젝트 고유 절차, 도메인 규칙, 사고 사례는 두고 간다. 역할, 틀, 훅은 테스트와 함께 가져간다
3. 다시 만들 수 없는 산출물(사람 검수 결과, LLM으로 만든 평가 세트, 유료 호출 기록)을 목록으로 뽑아 보관한다. 다시 만들 수 있는 것은 지문(SHA-256)만 문서에 남긴다
4. `_workspace/`는 보관하거나 지운다. 결론은 이미 추적 문서에 있어야 한다
5. 병행 세션과 worktree를 정리한다

## 8. 산출물 검증과 행동 강제 장치

규칙 문장은 에이전트가 그 문장을 따를 때만 지켜지므로, 세션이 바뀌고 맥락이 길어지면 흐려진다. 기계 장치는 둘로 나눈다. 산출물이 맞는지 판정하는 장치(8-1)와 명령·행동을 막는 장치(8-2)다. 비용이 달라 기준도 다르다.

### 8-1. 산출물 검증

스키마, lint, 테스트, 측정 스크립트처럼 산출물을 읽어 명령 하나의 종료 코드로 판정하는 장치다. 사고를 기다리지 않는다. 정본(설계 문서, 콘텐츠 계약, 디자인 기획)이 승인되면 같은 작업에서 그 계약을 검증으로 옮긴다. 규칙을 더하기 전에 아래 순서로 묻고, 앞 칸에서 풀리면 뒤 칸으로 가지 않는다.

1. 구조로 틀린 상태를 만들 수 없게 할 수 있나(스키마의 허용 값, 컴포넌트가 받는 필드, 공유 상수 한 곳)
2. 산출물을 읽는 테스트·lint·측정으로 판정할 수 있나. 예외는 허용 목록 한 줄로 두고 규칙 문장을 고치지 않는다
3. 둘 다 안 되는 판단만 규칙 문장으로 둔다. 정본 한 곳에 두고 삭제 조건을 적는다

- 검증이 막는 규칙은 스킬·에이전트에 다시 적지 않고 그 명령을 가리킨다. 문장과 검증이 함께 있으면 바꿀 때 둘을 맞춰야 한다
- 결정 기록·변경 이력 같은 과정 문서를 검사하는 장치는 형식 검사 이상으로 키우지 않는다. 문서를 맞추는 일만 늘고 산출물은 나아지지 않는다
- 오래 걸리는 검증(브라우저 측정 등)은 바뀐 대상만 보는 범위 옵션을 함께 둔다. 작은 수정에서 전체를 다시 돌지 않게 하기 위해서다

이유: 끝까지 지켜진 것은 스키마·테스트처럼 기계가 판정하는 것이었다. 글로 둔 규칙은 예외가 생길 때마다 문장을 고쳐야 하는 부채가 됐고, 같은 규칙이 여러 파일로 복사되며 작은 수정에도 여러 파일을 고치게 했다(portfolio 2026-11-17 회고).

### 8-2. 행동 강제 장치

hook, 권한 거부, 확인 창처럼 에이전트·사용자의 명령을 막거나 확인을 띄우는 장치다. 오탐이 잦으면 사용자가 장치를 끄고 하네스가 무력화되므로, 실수 한 번마다 더하지 않는다. `harness:evolve` 반영 전 관문(가·나)을 거친 항목에 이 기준을 적용한다. 3절 보호 장치처럼 구축 때 사용자가 말한 위험을 막는 장치는 되풀이를 기다리지 않는다.

- 장치는 두 조건을 모두 갖춘 실패에만 더한다. (1) 규칙 문장이나 그 문장이 불리는 위치를 고친 뒤에도 같은 실패가 되풀이됐다 (2) 실패를 기계로 판정할 수 있다(명령, 파일 내용, 검사 결과로 참·거짓이 갈린다)
- 자연어 판단이 필요한 실패(질문 형식, 정본과의 대조, 범위 판단)는 규칙과 작성 맥락이 없는 분리 검토로 둔다. 장치로 만들면 잘못 잡거나 놓친 경우를 사람이 다시 판정해야 해서 확인 창만 는다
- 장치를 더할 때는 3절처럼 막을 대상과 삭제 조건을 결정 기록에 적는다
