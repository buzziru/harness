# git·PR 흐름 (로컬 추가, 선택)

> 로컬 포크에서 더한 문서다. 근거는 portfolio 하나라 가설이다(`LOCAL_CHANGES.md`). 1단계 7에서 git·PR 흐름을 하네스에 넣기로 했을 때만 2절 이하를 읽는다.

git·PR 흐름은 하네스 밖의 작업 순서다. 브랜치, 커밋, PR, PR 전 검토, CI, 병합 뒤 정리, 세션 인수인계가 여기에 든다. 정하지 않고 시작하면 프로젝트가 이 흐름을 사고마다 하나씩 만들게 되고, 정해 두면 작은 프로젝트나 탐색 작업에는 짐이 된다. 그래서 넣을지와 수준을 사용자가 고른다.

## 목차

1. 넣을지와 수준(1단계 7의 질문)
2. 정할 항목과 선택지
3. 기본 프리셋의 세부 절차
4. 고른 값의 기록

## 1. 넣을지와 수준

1단계 7에서 운영 틀 질문과 함께 묻는다. 질문 형식은 `project-governance.md` 2절을 따른다. 질문 문장 예: "git 브랜치·커밋·PR·CI·세션 인수인계 같은 흐름을 하네스 규칙으로 둘까요? 작은 프로젝트나 탐색 작업에는 짐이 됩니다."

| 수준 | 생기는 것 | 맞는 경우 | 부담 |
| --- | --- | --- | --- |
| 넣지 않음 | 없음 | git을 쓰지 않거나, 혼자 짧게 하는 탐색·일회성 작업 | 없음. 대신 커밋 단위와 병합을 매번 사람이 정한다 |
| 가벼운 흐름 | 2절의 통합 방식, 브랜치 이름, 하네스 변경 분리, 보호 확인, 커밋 규칙. `CLAUDE.md` Git 절 몇 줄 | 혼자 하지만 기록을 남기는 프로젝트, main 푸시가 곧 배포인 저장소 | 브랜치 전환 정도 |
| 전체 흐름 | 가벼운 흐름에 더해 PR 과정, PR 전 분리 검토, CI 필수 검사 확인, 병행 PR의 기록 파일 충돌 처리, 병합 뒤 정리, 세션 인수인계 | 공개 저장소, 여러 세션이 병행하는 프로젝트, 사람이 PR 단위로 검토하는 프로젝트 | 검토 에이전트와 CI 설정, PR마다 검토·대기 몇 분. 정해 두지 않으면 이 흐름을 만드는 하네스·규칙 PR이 초반을 채운다 |

수준을 고른 뒤 2절에서 그 수준에 해당하는 항목만 정한다.

## 2. 정할 항목과 선택지

기본 프리셋은 한 사용자의 지금 설정이다. 다른 값을 고르면 3절의 해당 절차를 그 값에 맞게 바꾼다.

| 항목 | 선택지 | 기본 프리셋 | 선택지별로 맞는 경우 |
| --- | --- | --- | --- |
| 통합 방식(가벼운) | main 직접 커밋(trunk) / main에서 짧은 브랜치 + PR / 오래 사는 통합 브랜치(git-flow 계열) | 짧은 브랜치 + PR, main 직접 커밋 금지 | trunk: 혼자, 배포와 무관한 저장소. 짧은 브랜치 + PR: main 푸시가 배포이거나 변경을 검토한 뒤 합칠 때. git-flow 계열: 릴리스 주기가 따로 있는 저장소 |
| 브랜치 이름(가벼운) | 주제만 / 카테고리 접두어 + 주제 / 날짜·작업 번호 | 접두어(`feat/`, `fix/`, `docs/`, `chore/`, `harness/`) + 주제 | 주제만: 브랜치가 적을 때. 접두어: 브랜치가 많아 종류로 훑어야 할 때. 날짜·작업 번호: 이슈 추적기와 묶을 때 |
| 하네스 변경 분리(가벼운) | 작업 브랜치에 섞음 / 첫 푸시 전에 나눔 | 나눔 | 섞음: 하네스를 거의 고치지 않을 때. 나눔: 하네스 변경을 따로 검토·되돌려야 할 때 |
| 보호 확인(가벼운) | 확인 없음 / 1단계에서 확인해 `CLAUDE.md`에 적음 | 확인해 적음 | 확인 없음: 비공개이고 배포와 무관한 저장소. 확인해 적음: main 푸시가 배포이거나 공개 저장소(이때는 필수) |
| 커밋 규칙(가벼운) | 메시지 형식, 성격별 분리 여부, 스테이징 방식 | 성격별 분리, 파일 지정 스테이징, 메시지 형식은 프로젝트가 정함, 메시지를 재사용하는 amend 금지 | 파일 지정 스테이징: 사용자가 미커밋 변경을 함께 두는 작업 디렉터리. 성격별 분리: 커밋 단위로 되돌리거나 검토할 때 |
| PR 올리는 주체(전체) | 사용자 / 메인(검토 통과 시 승인 없이) | 메인 | 사용자: PR 전 검토를 두지 않을 때. 메인: PR 전 검토를 둘 때 |
| 병합 주체(전체) | 사용자 / 메인 | 사용자 | 사용자: 병합이 배포이거나 사람이 마지막으로 볼 때. 메인: CI와 검토를 모두 자동으로 믿을 수 있을 때 |
| PR 범위(전체) | 방향 하나에 PR 하나 / 날짜·세션 단위 | 방향 하나에 PR 하나 | 방향 하나: 리뷰를 사람이 할 때. 날짜·세션 단위: 리뷰 없이 기록만 남길 때 |
| PR 전 검토(전체) | 없음 / 작성 맥락 없는 검토 에이전트 | 검토 에이전트, 라운드 상한 2 | 없음: 사람이 PR마다 전체를 읽을 때. 검토 에이전트: 사람은 검토 안내만 읽을 때 |
| CI 필수 검사(전체) | 없음 / CI 실행만 / 병합 조건으로 건 필수 검사 | 필수 검사 | 없음: 판정 방법(`project-governance.md` 1절)이 사람 확인뿐일 때. CI 실행만: 실패해도 병합할 수 있어야 할 때. 필수 검사: 판정 방법이 명령으로 돌 때 |
| 병행 PR 기록 파일(전체) | 처리 규칙 없음 / 충돌 처리 규칙 | 규칙 둠 | 규칙 없음: PR이 하나씩만 열릴 때. 규칙 둠: 이력·결정 목록 끝에 행을 더하는 PR이 동시에 열릴 때 |
| 병합 뒤 정리(전체) | 수동 / 메인이 확인 뒤 삭제 | 메인이 확인 뒤 삭제 | 수동: 브랜치가 적을 때. 메인이 확인 뒤 삭제: 브랜치가 쌓이는 프로젝트 |
| 세션 인수인계(전체) | 없음 / 넘김 문서 | 넘김 문서 | 없음: 작업이 한 세션에서 끝날 때. 넘김 문서: 한 작업이 여러 세션에 걸칠 때 |

git 작업(커밋, 푸시, PR 생성, 병합, 브랜치 삭제, 인수인계)을 누가 하는지는 고른 값대로 `project-governance.md` 2절 자율 범위 표에 넣는다.

## 3. 기본 프리셋의 세부 절차

고른 항목의 절차만 오케스트레이터와 `CLAUDE.md` Git 절로 옮긴다.

### 브랜치

- 작업마다 main에서 짧은 브랜치를 내고 PR로 합친다. 접두어는 이름 안의 구분자일 뿐 상위 브랜치가 아니다. git은 `feat`와 `feat/x`를 함께 둘 수 없으므로 접두어 이름의 브랜치를 따로 만들지 않는다
- 하네스 변경과 작업 변경이 섞였으면 첫 푸시 전에 브랜치를 나눈다. 푸시 뒤에 나누면 이미 열린 PR의 범위가 바뀐다

### 보호 확인

- 1단계에서 main 푸시가 곧 배포인지, 보호 규칙(필수 검사, 강제 푸시·삭제 금지)이 있는지, 공개 저장소인지를 확인해 `CLAUDE.md` Git 절에 적는다. 보호 장치 전반은 `project-governance.md` 3절이다
- 강제 푸시가 막힌 환경에서 브랜치가 main과 갈라지면 rebase 대신 main을 병합해 푼다

### 커밋

- 성격이 다른 변경은 나눠 커밋한다. 한 파일에 섞였으면 줄 단위로 나눈다
- 파일을 지정해 스테이징한다(`git add -A`, `git add .` 금지). 사용자가 작업 중인 미커밋 변경을 넣지 않기 위해서다
- 메시지를 재사용하는 amend(`--amend --no-edit`, `-C HEAD`)를 쓰지 않는다. 앞 커밋의 설명이 새 변경에 붙는다

### PR

- 방향 하나에 PR 하나. 사용자 판단은 PR이 아니라 작업 중 대화에서 받는다(`project-governance.md` 5절)
- 본문은 검토 안내다: 이미 정한 것의 요약, 되돌리기 어려운 변경, 사람이 볼 곳, 읽지 않아도 되는 파일
- PR 전 검토가 `ready`면 메인이 승인 없이 푸시하고 PR을 연다

### PR 전 검토

- 작성 맥락이 없는 검토 에이전트가 브랜치 변경 전체를 보고 `ready` 또는 `blocked`를 낸다. 점검: 계획 대비 범위, 규칙 위반, 판정 방법(테스트 등) 통과, 남은 사용자 판단, 정본 변경이 하네스 파일까지 퍼졌는지(`SKILL.md` 4-5)
- 라운드 상한은 2. 2라운드부터는 직전 보고서와 변경분만 본다(`team-patterns.md` 1-4)
- 커밋 메시지에 대한 권고만 남았고 아직 푸시 전이면 메인이 고치고 다시 검토하지 않는다

### CI

- 판정 방법(`project-governance.md` 1절)을 CI 필수 검사로 연결하고 main 보호 규칙의 병합 조건으로 건다
- PR을 연 뒤와 PR 브랜치에 푸시할 때마다 `gh pr checks <번호> --watch --required`로 결과를 본다
- 필수 검사가 목록에 없으면 먼저 병합 충돌을 본다. 충돌이 있는 PR에서는 GitHub Actions `pull_request` 워크플로가 시작되지 않는다

### 병행 PR의 기록 파일 충돌

- 변경 이력이나 결정 목록 끝에 행을 더하는 PR이 여럿 열리면 뒤 PR이 충돌한다. 먼저 병합된 쪽 뒤에 main을 병합해 두 행을 날짜순으로 남긴다
- 결정 번호는 브랜치를 낼 때 잡고 병행 세션의 공유 기록(`parallel-sessions.md`)에 적어 겹치지 않게 한다

### 병합 뒤 정리

- 병합된 PR이 있고 `git merge-base --is-ancestor <브랜치> origin/main`이 참인 브랜치만 지운다. PR 확인을 빼면 막 만든 빈 브랜치도 조상 검사를 통과한다
- 브랜치에 병합되지 않은 커밋이 쌓였으면 지우기 전에 다른 브랜치로 옮긴다. `git branch -D`를 쓰지 않는다
- 원격 브랜치는 GitHub의 병합 뒤 자동 삭제 여부를 먼저 본다

### 세션 인수인계

- 넘김 문서의 절: 먼저 확인할 것(저장소 상태), 다음 단계, 밀린 계획, 계획 밖으로 한 일, 참고(경로만)
- 단계 경계에서만 넘긴다. 단계 중간에 넘기면 받는 쪽이 반쯤 된 산출물을 다시 판단해야 한다
- 넘김 문서는 작업 중에 지우지 않고 다음 핸드오프에서 덮어쓴다. 덮어쓰기 전에 앞 문서의 남은 항목이 새 문서나 대기 목록에 옮겨졌는지 대조한다
- 받는 쪽은 '먼저 확인할 것'을 저장소와 대조한 뒤 시작한다
- 메모리에 넘김 문서의 위치를 한 줄 둔다

## 4. 고른 값의 기록

- 수준과 항목별 값은 `project-governance.md` 4절 형식의 결정 기록으로 남기고, 프로젝트 `CLAUDE.md` Git 절에 값과 근거 결정 번호를 적는다
- 기본 프리셋과 다른 값을 고르면 결정 기록에 고른 이유를 적는다. 나중에 값을 바꿀 때 그 이유가 아직 맞는지 본다
