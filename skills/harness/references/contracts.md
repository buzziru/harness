# 노드 계약 (로컬 추가)

하네스의 단계(노드)마다 무엇을 받고, 어디까지 쓰고, 언제 끝나고, 언제 멈추는지를 한 파일에 정한다. 계약은 경계를 다룬다. 산출물의 품질(글의 설득력, 디자인 취향)은 계약 칸으로 옮기지 않고 사람 게이트가 판정한다. 경계가 분명하면 에이전트가 맡은 판단과 사용자가 풀어야 할 문제가 갈라져 보인다.

## 1. 노드와 게이트

- 노드는 에이전트 호출 한 번(`kind: agent`) 또는 사람의 판정 한 번(`kind: human`)이다. 같은 에이전트를 트랙마다 다른 입력으로 부르면 노드를 따로 둔다. 계약을 에이전트에 붙이면 경우를 가르는 문장이 에이전트 정의에 쌓인다
- 기획과 최종 검증은 사람 게이트 노드로 둔다. 기획 게이트의 출력은 중간 노드가 기대는 전제(평가 지표, 검증 방식, 범위, 인터페이스)다. 중간 노드는 그 전제 안에서 자율로 진행한다
- 중간 구간의 폭은 도메인이 정한다. 중간 산출물을 명령으로 판정할 수 있으면(코드, 지표, 테스트) 넓고, 산출물 자체가 글·디자인이면 좁다. 사람 게이트는 줄여야 할 결함이 아니라 남는 최종 상태다

## 2. 파일 형식

`.claude/harness.json`의 `contracts`가 계약 파일(JSON)을 가리킨다. 이 파일이 노드 사이 데이터 전달의 정본이다. 에이전트 정의는 맡은 노드 id만 가리키고 입력·출력 규칙을 따로 적지 않는다. 오케스트레이터는 노드 id로 순서·분기·승인을 적는다.

```json
{
  "nodes": {
    "plan": {
      "kind": "human",
      "inputs": [{"path": "_workspace/00_brief.md", "from": null, "required": true}],
      "outputs": [{"path": "docs/plan.md", "check": "형식: 목표, 전제"}]
    },
    "analysis.run": {
      "kind": "agent",
      "agent": "analyst",
      "skill": "analysis",
      "inputs": [{"path": "docs/plan.md", "from": "plan", "required": true}],
      "outputs": [
        {"path": "reports/<topic>.md", "check": "형식: 결론, 근거"},
        {"path": "_workspace/<topic>/NN_analyst_log.md", "check": "미정", "required": false}
      ],
      "writes": ["reports/<topic>.md", "_workspace/<topic>/**"],
      "delegated": ["그림 종류 고르기"],
      "stop": {
        "contract": ["원자료 수정이 필요함"],
        "premise": ["검증 점수와 기획 전제의 지표가 어긋남"]
      },
      "parallel": [],
      "note": "자유 설명"
    }
  }
}
```

| 칸 | 뜻 |
| --- | --- |
| `inputs[]` | `path`, 만든 노드 `from`(밖에서 오면 `null`), `required` |
| `outputs[]` | `path`, `check`, `required`(없으면 true). `check`는 `미정`, `형식: 제목, …`(md는 제목, json은 최상위 키), 명령(종료 코드 0이 통과) 가운데 하나 |
| `writes` | 노드가 바꿀 수 있는 파일 범위. 출력 경로에서 시작해 넓힌다 |
| `delegated` | 에이전트에게 맡긴 판단 |
| `stop.contract` | 계약 밖 일이 필요할 때. 하지 않고 멈춰 보고한다 |
| `stop.premise` | 기획 전제가 깨졌을 때. 기획 게이트로 돌아간다 |
| `parallel` | 함께 도는 노드. 서로 `writes`가 겹치면 안 된다 |

출력 경로는 `reports/<topic>.md`처럼 고정 폴더로 시작하게 쓴다. 노드 검사는 출력 경로의 고정 접두(와일드카드 앞까지)에 든 폴더만 훑는다. `<slug>/report.md`, `*.md`, `report_NN.md`처럼 고정 접두에 폴더가 없으면 프로젝트 루트 전체를 훑는다. 와일드카드가 없는 경로는 그 파일 하나만 본다.

경로에서 `**`, `*`는 glob, `<이름>`은 경로 한 칸(실행 때 값을 채움), 앞뒤가 영문자가 아닌 `NN`은 숫자다(`NN_report.md`의 `NN`은 숫자, `PLANNING.md`는 글자 그대로).

## 3. 처음부터 두는 최소 형식

사용자가 계약을 다 그리지 못해도 구축 때 모든 칸을 둔다. 메인이 작업 흐름과 저장소를 읽고 채우며 사용자에게 묻지 않는다.

- `inputs`, `outputs`의 경로, `writes`는 처음부터 채운다
- 판정 기준을 아직 모르는 출력은 `check: 미정`으로 둔다. 칸을 비우지 않고 `미정`으로 두어야 아직 정하지 않은 경계가 개수로 보인다
- `delegated`, `stop`은 비어 있어도 배열로 둔다
- 결정 번호를 적지 않는다(`project-governance.md` 4절)

형식은 `scripts/check-harness.mjs --stage build`의 C1\~C6이 검사한다. 검사는 구조까지만 보고 계약이 적절한지는 보지 않는다(`project-governance.md` 8-1). `--stage evolve`는 `contracts` 키가 없는 이전 하네스에서 C 검사를 건너뛴다. 그런 하네스에 계약을 들일 때는 `harness` 스킬의 기존 구성 확장으로 2-4를 한다.

## 4. 실행 때

1. 메인은 에이전트 노드를 부르기 전에 `check-harness.mjs --stage node --node <id> --mark`로 작업 트리 상태를 남긴다
2. 에이전트에게 노드 id와 `<이름>` 값을 넘긴다. 에이전트는 계약 파일에서 자기 노드를 읽는다
3. 에이전트는 반환 다섯 칸으로 답한다
   - 산출물: 경로
   - 검사: `check` 명령과 종료 코드
   - 멈춤: `없음` 또는 `계약`·`전제`와 사유
   - 계약 밖: 필요했지만 하지 않은 일
   - 판단: `delegated` 안에서 한 판단, 그 밖에서 한 판단
4. 메인은 `--stage node --node <id> [--var 이름=값]`을 돌린다. N1은 표시 뒤 바뀐 파일이 `writes` 안인지 본다. gitignore된 파일은 보지 않고, `parallel` 노드(어느 쪽에 적었든)의 `writes`에 든 파일은 그 노드의 검사에 맡긴다. 같은 작업 트리에서는 어느 노드가 썼는지 가를 수 없어서, 함께 도는 노드끼리 서로의 `writes`에 쓴 것은 잡지 못한다. C5는 두 범위가 겹치지 않게만 한다. N2는 필수 출력이 표시 뒤 생기거나 바뀌었는지(gitignore된 폴더 포함)와 형식 칸이 있는지 본다. 위반은 보고하고 되돌릴지는 메인이 정한다. 같은 위반이 되풀이되기 전에는 hook으로 막지 않는다(`project-governance.md` 8-2). `check` 명령은 에이전트가 돌린 판정을 이어받는다(`team-patterns.md` 1-4)
5. 멈춤이 `계약`이면 메인이 계약 밖 일을 맡을 노드를 고르거나 사용자에게 묻는다. `전제`면 기획 게이트로 돌아간다

최종 게이트에 넘기는 보고에는 세 칸을 고정으로 둔다. 이번 실행에서 `check: 미정`으로 남은 출력, 계약 밖 보고, `delegated` 밖에서 한 판단이다. 사용자는 다음에 정할 경계를 여기서 본다. 그래서 실행 중에 질문을 더할 필요가 없다. 게이트 기록(판정, 사유, 세 칸)은 frame이 정한 결정 기록 위치에 남겨 `harness:evolve`가 읽게 한다.

## 5. 계약이 분명해지는 경로

`harness:evolve`가 게이트 기록을 입력으로 계약을 고친다.

| 되풀이된 것 | 고칠 곳 |
| --- | --- |
| 같은 계약 밖 보고 | `writes`·`inputs`를 넓히거나 노드를 새로 둔다 |
| 같은 판단, 기준이 생김 | 출력의 `check`를 `형식:`이나 명령으로 올린다 |
| 같은 판단, 맡겨도 됨 | `delegated`에 더한다 |
| 출력이 모두 명령으로 판정되는 중간 노드 | 반려 이력이 없을 때만 그 노드의 승인 지점을 빼자고 제안한다. 최종 게이트는 대상이 아니다 |

`check: 미정` 수는 `--stage evolve`의 정보 줄로 나온다. 이 수가 줄어드는 추이로 계약이 분명해지는 정도를 본다. 승인 지점은 그 결과로 준다.

## 6. 그래프 런타임과의 관계

노드와 `from` 연결이 그래프이고, `kind: human` 노드는 사람 입력을 기다리는 지점이다. 지금은 메인이 오케스트레이터를 읽고 이 그래프를 직접 운영한다. 나중에 런타임이 같은 파일을 읽게 할 수 있도록, 순서·분기를 판단하는 데 필요한 사실(입력, 출력, 멈춤 종류)은 계약 파일에 두고 오케스트레이터에 다시 적지 않는다.
